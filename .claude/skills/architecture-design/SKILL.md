# 아키텍처 설계 (A-SPICE SWE.2)

입력은 승인된(또는 검토된) 요구사항 `docs/requirements/`이다. 산출물은 `docs/architecture/`에 둔다.
요구사항이 없으면 설계를 시작하지 말고 `/requirements-analysis`를 먼저 하도록 안내한다.

## 규칙

1. **컴포넌트 정의**: 모든 컴포넌트는 `ARC-nnn` ID, 책임(한 문장), 담당 요구사항(`SWR-…`), 포함 모듈(상세 설계에서 채움)을 가진다.
2. **인터페이스 필수**: 모든 컴포넌트는 최소 하나의 인터페이스(`IF-nnn`)를 가진다. 인터페이스 정의 없는 컴포넌트는 허용하지 않는다.
3. **인터페이스를 통한 통신만 허용**: 컴포넌트 간 의존은 오직 `IF-nnn`을 통해서만 존재한다.
   다른 컴포넌트의 내부 헤더/타입/전역 변수에 직접 접근하는 설계를 하지 않는다. 의존 관계 표에 "컴포넌트 → IF"만 기록하고 "컴포넌트 → 컴포넌트"는 기록하지 않는다.
4. **응집도 높게, 결합도 낮게**: 한 컴포넌트는 한 가지 이유로만 변경되어야 한다. 순환 의존을 금지하고, 의존 방향은 상위 정책 → 추상 인터페이스 ← 세부 구현으로 한다.
5. **모듈화·캡슐화**: 내부 구현 상태와 타입은 컴포넌트 안에 숨기고 인터페이스로만 노출한다.
6. **SOLID**: 단일 책임, 개방-폐쇄, 리스코프 치환, 인터페이스 분리(작고 목적이 분명한 인터페이스), 의존성 역전을 설계 결정마다 점검한다. 위반하는 결정은 근거와 함께 기록하고 리뷰에서 승인받는다.

## 산출물 형식

`docs/architecture/architecture.md` (필수 절)
1. 개요와 설계 결정 및 근거(대안과 선택 이유)
2. 컴포넌트 목록 – 각 `### ARC-nnn <이름>` 제목 아래 책임, 담당 SWR, 제공 IF, 사용 IF
3. 인터페이스 정의 – 각 `### IF-nnn <이름>` 제목 아래 아래 표
4. 컴포넌트 의존 관계 (Mermaid 다이어그램 + "컴포넌트 → IF" 표)
5. 동적 동작 (핵심 시나리오의 호출 순서, 필요 시 상태 전이)
6. 자원 소비 목표 (요구된 제한 `SWR-LIM`의 할당)

인터페이스 정의 표 (`IF-nnn`마다 필수)

| 항목 | 내용 |
|------|------|
| 제공자 / 사용자 | `ARC-…` / `ARC-…` |
| 시그니처 | 함수 선언 또는 메시지 형식 (반환값은 상태 코드, CLAUDE.md의 구현 규칙 참조) |
| 입력 / 출력 | 타입, 단위, 범위, 소유권 |
| 사전/사후 조건 | |
| 오류 처리 | 반환 가능한 상태 코드와 의미 |
| 호출 순서·스레드·시간 제약 | |

## 추적성

- `SWR → ARC` 링크를 `docs/traceability/links.csv`에 추가한다. 모든 `SWR`이 하나 이상의 `ARC`에 할당되어야 하고, 모든 `ARC`는 하나 이상의 `SWR`에서 나와야 한다.
- 인터페이스 `IF`는 제공하는 `ARC` 아래에 `ARC-nnn,IF-nnn`으로 연결한다.
- 검사: `python -I .claude/skills/requirements-analysis/scripts/check_traceability.py --until arch`

## 완료 조건

1. 모든 컴포넌트가 인터페이스를 가지고, 컴포넌트 간 직접 의존이 없다.
2. 순환 의존이 없다. (의존 표로 확인)
3. 추적성 검사(`--until arch`)가 통과한다.
4. `/review architecture`로 리뷰하고 결과를 `docs/reviews/`에 남긴다.
