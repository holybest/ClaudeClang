# 시스템 테스트 리뷰 체크리스트 (SWE.6)

대상: `tests/system/*.json`(`/sw-system-test-case` 입력 데이터), 생성된 Excel, `tests/system/results.csv`(실행 결과).

| ID | 점검 항목 |
|----|-----------|
| ST-01 | `docs/requirements/`의 **모든 `SWR`이 시험 가능한 베이시스로 등록**되어 있고 제안이 아닌 테스트 케이스로 1개 이상 커버된다 (요구사항 커버리지 100 %). `python3 ci/scripts/system_test_gate.py` 결과를 인용한다. |
| ST-02 | 시험 불가(`testable: false`)로 표시된 요구사항이 없다. 있다면 사유와 `findings`가 있고, 그 요구사항을 어떻게 해결할지(요구사항 수정 등)가 정해져 있다. 숨겨서 100 %처럼 보이게 하지 않았다. |
| ST-03 | 모든 테스트 케이스가 존재하는 베이시스 ID에 추적된다 (고아 케이스 없음). 베이시스 ID가 `docs/requirements/`의 `SWR` ID와 일치한다. |
| ST-04 | 스킬의 검증(`build_workbook.py --check-only`)이 오류 없이 통과한다. 검증 규칙을 우회하거나 필수 항목을 형식적으로 채우지 않았다. |
| ST-05 | 케이스마다 **고유한 목적**이 있다. 같은 동치 클래스·같은 경계·같은 동작을 반복하는 케이스, 커버리지 숫자만 채우는 케이스가 없다. |
| ST-06 | 동치 분할과 경계값 분석이 요구사항의 입력·상태에 적용되었다. 무효 클래스는 한 케이스에 하나씩만 넣었다. |
| ST-07 | 독립 이산 파라미터가 3개 이상인 곳에는 **PICT**로 페어와이즈를 만들었고, 모델·옵션·시드·결과가 `pict_models`에 있으며 결과 행을 임의로 빼거나 바꾸지 않았다. 사용하지 않았다면 사유가 있다. |
| ST-08 | 입력값이 구체적이다(실제 값과 단위). "적절한 값", "정상 범위" 같은 표현이 없다. |
| ST-09 | 절차가 재현 가능하다: 사전조건 → 조작 → 대기 시간 → 관찰 순서로 번호가 매겨져 시험자가 혼자 따라 할 수 있다. |
| ST-10 | 예상 출력과 합격 기준이 **판정 가능**하다: 관찰 신호, 기대값, 허용오차, 시간 제한이 있다. "정상 동작", "올바르게 처리" 같은 표현이 없다. |
| ST-11 | 시험 환경(HIL/SIL/벤치 등)에서 실제로 주입·관찰할 수 있는 신호만 쓴다. 관찰 불가능한 내부 변수에 의존하지 않는다. |
| ST-12 | 제안 케이스(`suggested: true`)가 "제안"으로 구분되어 있고 관련 베이시스에 추적된다. 연결할 베이시스가 없는 제안은 `findings`에 "요구사항 추가 필요"로 기록되었다. |
| ST-13 | 요구사항의 모호·누락·모순이 `findings`로 기록되었고, 시험 설계자가 값을 추측해서 채우지 않았다. |
| ST-14 | 비기능 요구사항(타이밍, 자원, 신뢰성)에 측정 방법·횟수·부하 조건·허용 기준이 있다. 안전 관련 항목(ASIL)에는 고장 주입 등 필요한 방법이 고려되었다. |
| ST-15 | **모든 테스트 케이스(제안 포함)에 실행 결과가 있고 최신 결과가 `PASS`이다** (성공률 100 %). `tests/system/results.csv`에 미실행·`FAIL`이 없다. |
| ST-16 | 결과의 실행자·일시가 기록되어 있고, 실패 후 재실행했다면 원인 분석과 수정이 이력으로 남아 있다(실패를 지우거나 덮어쓰지 않았다). |
| ST-17 | 생성된 Excel이 JSON 원본과 일치한다 (Excel을 직접 고치지 않았다). |
| ST-18 | 상위(요구사항)·하위(시험 결과) 양방향 추적성이 유지된다. 요구사항 변경이 있었다면 영향받는 케이스가 갱신되었다. |
